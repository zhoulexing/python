# L0全量目录与零售表明细方案

## 1. 目标

在系统提示词中放入 150 张表的极简信息（L0），避免上下文爆炸；在生成 SQL 时，再按需读取表明细（L1/L2）。  
本文件给出：

- 150 张表可复用的 L0 结构模板
- 当前零售销售核算表的 L0 示例
- 当前表的完整明细（维度/度量/聚合规则/风险标签）

---

## 2. L0 技能卡片模板（推荐）

你要的“像技能一样”的 L0，建议统一成卡片格式。  
每张表只保留 3 个核心信息 + 1 行约束：

- 表名称
- 表 ID
- 表描述（重点写“这张表具体能做啥”）
- 使用约束（可选，1 行）

### 2.1 卡片模板（可批量复制）

```text
[表名称]
表ID: <table_id>
表描述: <这张表能回答哪些业务问题，列 2~4 个典型场景>
使用约束: <可选，如 必带租户过滤 / UV不可直接求和 / 字符串计数需转型>
```

### 2.2 用于系统提示词的轻量结构（可选 JSON）

```json
{
  "table_name": "<表名称>",
  "table_id": "<table_id>",
  "table_desc": "<这张表具体能做啥>",
  "usage_constraints": ["<约束1>", "<约束2>"]
}
```

## 4. 当前表明细（L1/L2）

### 4.1 表级明细

- `table_id`: `10`
- `physical_table`: `dm_retail.retail_sales_detail_team_src_fin_logistics`
- 业务说明：零售销售核算小时事实表，覆盖店铺、渠道、物流、会员、地理等分析视角
- 默认时间字段：`natural_day`
- 建议租户过滤：`kdt_id` 或 `hq_kdt_id`（必须）
- 主聚合规则：
  - 金额类：`sum(field)`
  - 计数字段（varchar）：`sum(toInt64OrZero(field))`
  - 比率类：`numerator / nullIf(denominator, 0)`

### 4.2 风险标签定义

- `varchar_count_need_cast`：部分计数字段为字符串，必须转型后聚合
- `uv_not_additive`：`paid_order_uv`/`top_up_uv`/`refunded_order_uv` 跨粒度不可直接累加
- `tenant_filter_required`：必须携带店铺或总部店铺过滤
- `time_field_string`：`natural_day` 为字符串日期，建议查询时转 `toDate(natural_day)` 做时间比较

## 5. 系统提示词建议写法（L0 全量 + 规则）

```text
你是一名 ClickHouse SQL 生成助手。
系统已提供 150 张表的 L0 目录（极简摘要），你必须先基于 L0 选择表，再使用该表明细规则生成 SQL。

必须遵守：
1) 必须包含租户过滤（kdt_id 或 hq_kdt_id）；
2) 计数字段若为 varchar，必须使用 toInt64OrZero 转型后再 sum；
3) UV 指标（paid_order_uv/top_up_uv/refunded_order_uv）跨粒度不可直接累加；
4) 时间过滤默认字段 natural_day，建议使用 toDate(natural_day) 比较；
5) 仅输出 SQL，不输出解释。
```
